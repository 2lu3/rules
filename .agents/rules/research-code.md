# 研究コードを扱う agent への指示

## 目的と前提

この指示を適用するプロジェクトは、単一の研究者が使用する研究コードである。
科学的に妥当な計算を、処理内容が追える最小限のコードで表現する。
計算の完走より、結果の信頼性、科学的な見通し、再現性を優先する。
前提が崩れた場合は原因を隠さず停止し、ユーザーが原因を調べて修正できるようにする。

Python の assert を無効化する実行方法は使用しない。
この実行前提は研究スクリプトと共通ライブラリの両方に適用する。

## エラーと入力検証

- Python の例外と traceback、外部コマンドのエラーを原則そのまま伝播させる。
  エラーを握りつぶしたり、警告だけ出して続行したり、成功扱いにしたりしない。
- 例外の型やメッセージを形式的に統一するためだけの catch / re-raise は追加しない。
  元の例外で原因が分かる場合は、その例外を利用する。
- 実行を通すための代替値、暗黙のスキップ、自動フォールバック、自動リトライを、
  明示された要件なしに追加しない。
- 入力条件、科学的前提、不変条件の検証には原則 assert を使う。
  条件違反で停止するだけなら、if + raise に書き換えない。
- assert のメッセージは、違反した条件や対象、必要な値を簡潔に示す。
  assert 内では検証だけを行い、計算実行やファイル書き込みなどの副作用を置かない。
- 通常の処理が明確に失敗する箇所には、同じ検証を重ねない。
  ファイル読み込みの FileNotFoundError、必須キー参照の KeyError、
  数値変換の ValueError などはそのまま伝播させる。
- 入力内容の検査でも、後続処理がその入力を消費する際に明確な元の例外を発生させて
  停止することが予期でき、失敗までに成果物の公開や重要な副作用がないなら、
  同じ内容の事前検証を重ねなくてよい。例えば、PDB の `ATOM` レコードの有無を
  後続の標準 PDB パーサーや構造処理が不正内容として検出するなら、前段で同じ検査を追加しない。
- ただし、「後でエラーになる可能性がある」だけで検証を削除しない。後続処理が実際に
  失敗すること、元のエラー原因を追跡できること、失敗前に成果物の公開や重要な副作用が
  発生しないことを確認して判断する。
- 自然には失敗しない誤りは、明示的に検証して停止させる。
  必須ファイル検索がゼロ件、対象データが空、列数・形状・原子対応の不一致、
  許容しない NaN / infinity、物理的制約への違反などが該当する。
- 検証は、その前提に依存する処理より前に行う。
  自然失敗では検出できない前提や、後続の長時間計算・書き込み・外部コマンド実行を
  始める前に必要な入力を確認することには意味がある。
  同じ前提を各層で機械的に検証し直さない。
- 対象外のデータを仕様に従って除外することと、不正な対象データを無視することを区別する。
  例えば、ログの説明行は除外してよいが、解析対象の数値行が壊れている場合は停止させる。
- リソース解放や未完成ファイルの後始末に必要な context manager、try/finally は使用してよい。
  後始末でも元の失敗を隠さない。

判断基準は、入力内容については「後続処理が明確な元のエラーを自然に返して停止し、
原因を追跡でき、失敗前に成果物公開や重要な副作用がないなら検証を重ねない」、
それ以外は「自然には失敗しない誤りや重要な前提を明示的に検証する」とする。
コードを短くするために必要な検証を削除しない。

```python
# ファイル欠落は読み込み処理が検出する。
text = input_path.read_text()

# 空の検索結果は自然には失敗しないため、検証する。
files = sorted(input_dir.glob("*.pdb"))
assert files, f"No PDB files found in {input_dir}"

# 計算できてしまう前提違反を検出する。
assert positions.shape == reference.shape, "Coordinate shapes must match"
assert np.isfinite(positions).all(), "Coordinates contain NaN or infinity"
```

## 外部コマンドと処理の継続

- 外部コマンドの失敗を呼び出し元へ伝播させ、後続処理を実行しない。
- Python の subprocess.run は原則 check=True を使う。
  終了コードを手動で assert するために check=False にしない。
- Bash は set -euo pipefail を基本とする。
  それだけであらゆる失敗が伝播すると仮定せず、使用する条件分岐やパイプラインでも
  失敗時に後続処理が走らない構造にする。
- stdout / stderr をログに保存する場合も、元のエラーを調べられるようにする。
- 非同期ジョブの準備・投入と、完了した結果の集計を明確に分ける。
  準備時に結果がないことは正常だが、集計に必要な結果が不足していれば停止させる。
  ジョブの投入成功を計算の正常終了として扱わない。

## 研究スクリプトの読みやすさ

- 入力、実験条件、科学的処理、出力の流れを直接読める構造にする。
- 科学的に意味のあるパラメータ、単位、選択条件、近似、閾値を明示する。
  今回の研究上の判断を、ライブラリのデフォルト値や深い呼び出し階層に隠さない。
- コードの短さより、科学的な意味を追いやすいことを優先する。
  意味の違う処理を無理に共通化しない。
- コメントは、科学的根拠や、その処理・前提が必要な理由を説明する。
- 欠損データの除外・補完、単位の推定、原子の再対応付け、収束条件の緩和など、
  結果の意味を変える処理を暗黙に追加しない。
- 入力、パラメータ、乱数 seed など、再現に必要な情報を追跡できるようにする。
  シンプルにするために再現性に必要な情報を省略しない。

## 研究スクリプトとライブラリの責務

- 研究スクリプトは、その実験の条件設定と処理手順を表現する。
- プロジェクト固有の再利用処理は、そのプロジェクトの共通ライブラリに置く。
- 複数のプロジェクトで科学的な意味と入力の前提が共通する処理は、汎用ライブラリに置く。
- ライブラリは、明示的な引数と戻り値を持ち、特定スクリプトのグローバル変数や
  実験設定に暗黙に依存しない。
- ライブラリは長期保守を前提とし、責務の明確さ、入出力契約、重複の削減、
  保守しやすさを重視する。ライブラリでもエラー時は停止してよい。
- 共通化する際は、処理とともに、その処理に必要な検証も適切なライブラリ側に置く。
  今回の実験条件を採用する判断は研究スクリプト側に残す。
- 将来使うかもしれないという理由だけで、汎用フレームワーク、クラス階層、
  設定項目、拡張ポイントを追加しない。
- 既存の共通処理を確認し、同じ機能を別の場所に重複実装しない。

### `steps`・`domain`・`ansel` の責務構造

研究コードの処理は、次の一方向の構造として組み立てる。

```text
研究の実行
└── steps       ワークフロー全体を進める
    └── domain  一つの業務上の操作を実現する
        └── ansel  小さく検証された処理を実行する
```

依存方向は `steps → domain → ansel` とする。上位層は下位層を組み合わせるが、下位層は
上位層の実行順、プロジェクト構成、実験固有の判断を知らない。

#### `steps`: 実験の流れを表す最上位層

`steps` は、実際のファイル配置・設定・実行コンテキストを解決し、`domain` の処理を
どの順番で呼ぶか、どの条件で分岐するかを表現する。ここで重要なのは、個々の処理を
再利用しやすく分割することではなく、実験の流れを上から読めることである。

そのため、`steps` の関数は基本的に細かく分割しない。大きな一つの関数に処理手順を
まとめることを許容し、関数分割は、分割しないと流れが読めない場合、または独立した
検証・再利用・副作用の境界が明確に存在する場合に限る。`steps` に `ansel` の低レベル
処理や `domain` の業務ルールを再実装しない。

#### `domain`: 業務上の操作を表す中間層

`domain` は、`ansel` の小さな処理を組み合わせて、一つのプロジェクト固有の業務操作を
実現する。各関数・オブジェクトは、業務上の責務を一言で説明できる大きさにする。
科学的な条件や不変条件の判断もここに置く。

`domain` は一つの業務操作の内部で必要な処理を組み合わせるが、ワークフロー全体の呼び
出し順や実行環境の解決は担当しない。また、`ansel` に置くべき低レベル操作を重複実装
しない。

#### `ansel`: 小さな処理を置く最下位層

`ansel` には、できるだけ小さく単一の責務を持つ関数を置く。各関数は小さな入力で
個別に検証でき、入力・戻り値・失敗条件を明確にする。処理の原子部分は、基本的に
`ansel` に集約する。

`ansel` の関数は環境非依存にする。`cwd`、固定されたプロジェクト構成、特定のファイル
配置、暗黙のグローバル設定を前提にしない。ファイルや外部リソースが必要な場合は、
パス・ストリーム・クライアントなどを明示的な引数または依存性として受け取り、どこから
取得するかの判断を関数内に埋め込まない。

#### 検証の単位

この構造に合わせて、検証の責務も下位から上位へ積み上げる。

```text
ansel   ── 関数単位の入出力・失敗条件
  ↓
domain  ── 業務ロジック・科学的条件・不変条件
  ↓
steps   ── domain の呼び出し順・分岐・環境からの引数変換
```

配置の具体例として、MD simulation のプロジェクトでは次のように分担する。移植先では、
同じ責務を持つライブラリ名に読み替える。`pytool` は将来 `ansel` に統合する既存処理を
置く場所とし、新たな責務の重複は避ける。

## 中間結果と成果物

- 途中結果と正常終了した成果物を区別する。
  処理が失敗した場合に、途中出力を完成した結果として後続処理へ渡さない。
- 以前の成果物が存在することだけで、今回の計算が成功したと判断しない。
- 作業ディレクトリの初期化など、後続処理の前提となる操作の失敗を無視しない。
  初回実行で対象が存在しないことを許容する仕様と、存在する対象の削除失敗を区別する。
- 既存の確定成果物を、リファクタリングに伴って自動削除・再計算しない。
  保存・公開方法は対象プロジェクトの明示された仕様に従う。

## 変更時の振る舞いと検証

- リファクタリングでは、正常入力に対する計算式、科学的条件、単位、結果の意味を維持する。
  科学的妥当性の再評価や条件変更が必要なら、構造整理とは分けて扱う。
- 通常の実装上の選択は、この方針と既存の仕様に従って進める。
  科学的な意味を決める必要がある曖昧さは、独断で補わずユーザーに確認する。
- テストは、既知の小さな計算例、科学的な不変条件、不正入力での停止、
  外部コマンドの失敗伝播など、結果の信頼性に関わる振る舞いを重視する。
- 移動・改名だけの変更に、実装をなぞるだけのテストを増やさない。
  変更によって影響する既存テストは更新し、必要な確認を行う。
- 例外の包み直しを削除した場合は、テストも元の例外や assert の契約に合わせる。
  旧例外型や装飾メッセージを維持するためだけの互換処理は追加しない。
- 小さな入力で正常時の結果を比較する。長時間計算や実環境へのジョブ投入が必要な確認は、
  実施済みの検証と未確認の部分を区別して報告する。
